# 2026.317.0614 — feat(pod): own the kind:pod body — #Pod/#PodValue move into the plugin's CUE module

## Summary

`opencharly/spec#304` unit 3, leg 1 (the producer): the `kind: pod` entity body moves from the contract module into the CUE module of the plugin that **serves** the kind, and that plugin declares the gate def on its capability in the SAME change.

The body lived in `spec/schema/pod.cue` (`#Pod`) with a `#PodValue` twin in `spec/schema/node.cue`, gated host-side through the `spec.KindValueDefs` compatibility fallback. `opencharly/charly#1122` established the contract for moving one: a kind whose body lives in its own plugin's CUE module must declare `InputDef: "#<Word>Value"` on its `class:kind` capability, or the host keeps answering from the base and the base can never drop the def. This change is that pair, plus the deletion of the last Go dependency the body still had.

**WHICH plugin, and why it is not `plugin-deploy-pod`.** `spec#304`'s own table names `plugin-deploy-pod` as the owner. Measured, exactly ONE provider serves `kind:pod`, and it is this one: `plugin-substrate`'s `substrateWords` declares `pod` beside the seven sibling substrate words and `NewMeta` emits `{Class: "kind", Word: w, Structural: true, DeployTraits: …}` for each, while `plugin-deploy-pod` declares only `{Class: "deploy", Word: "pod", InputDef: "", Lifecycle: true}`. A `kind` body belongs with the plugin that serves the kind, and a plugin's CUE module may import only the CONTRACT module — so the word's owner is the body's home. Moving the word to the deploy repo instead would split the eight-word substrate table (traits, status collectors, the OpLoad echo) across two plugins and duplicate it: R2 on sight. The recorded plan was corrected on the tracker with the measurement.

**What stays in the contract, and why.** `#PodSidecar` does not move. The contract's own `#ResolvedPod` (`spec/schema/substrate_template.cue`) cites it, and that envelope is what the kernel reads; the moved def references it as `schema.#PodSidecar`. This is the shape units 1 and 2 paid for (`#PipelineClassRoutes`, `#TaskParamSpec`) with one difference worth stating: there, a SIBLING plugin's schema pinned the def; here nothing in any plugin does — a cross-plugin sweep is EMPTY (`grep -rn 'schema\.#Pod'` over all 248 opencharly modules in the module cache and over every materialized plugin checkout returns zero citations; the one `#Pod` hit, `plugin-pod`'s `#PodPlugin`, is an unrelated def name). The pinning citation is the contract's own.

**`spec.Pod` is deleted from this plugin's dependency, not merely unread.** Its one and only reader in the whole tree was `resolve.go`'s OpResolve leg, which copied five fields out of `spec.Pod` into `spec.ResolvedPod`. The authored body's fields ARE that envelope's fields, so the arm now decodes the authored bytes straight into `#ResolvedPod` — and the contract's own note on `#ResolvedPod` already said the kernel "never" reads a `spec.Pod`. `charly` and `sdk` read it in zero files. The base's CUE def and its generated Go type follow in leg 2, on the tracker.

**The routing is unchanged.** The pod word still declares `DeployTraits`, so `IsStandaloneResourceKind` still sends it down `foldSubstrateKind`; the declaration only changes WHICH def the host value gate reads — the provider's declared `#PodValue` out of the composed unit, instead of the base's fallback.

**The declaration is data, not a per-word branch.** `substrateKindInputDefs` is a table beside `substrateTraits` (the file's own idiom), so a word cannot declare a gate def without also declaring its traits, and each sibling kind that moves later adds exactly one row.

**Pins.** `sdk` `v0.2026296.1207` → `v0.2026317.18` and `spec` `v0.2026296.1036` → `v0.2026317.51`, because `spec/schemacompose` (`ServedSchema`/`ServedText` — the offline import resolution both sides of the wire compose with) does not exist at the older spec pin. `go mod tidy` clean; this module is the repo's only Go module.
