# 2026.317.2232 — feat(local): own the kind:local body — #Local/#LocalValue move into the plugin's CUE module

## Summary

`opencharly/spec#304` unit 4, leg 1 (the producer): the `kind: local` entity body moves from the contract module into the CUE module of the plugin that **serves** the kind, and that plugin declares the gate def on its capability in the SAME change. The body lived in `spec/schema/local.cue` (`#Local`) with a `#LocalValue` twin in `spec/schema/node.cue`, gated host-side through the `spec.KindValueDefs` compatibility fallback. opencharly/charly#1122 established the contract for moving one: a kind whose body lives in its own plugin's CUE module must declare `InputDef: "#<Word>Value"` on its `class:kind` capability, or the host keeps answering from the base and the base can never drop the def. This change is that pair, plus the deletion of the last Go dependency the body still had.

**WHICH plugin, and why it is not `plugin-deploy-local`.** `spec#304`'s own table names `plugin-deploy-local` as the owner. Measured, exactly ONE provider serves `kind:local`, and it is this one: `plugin-substrate`'s `substrateWords` declares `local` beside the seven sibling substrate words and `NewMeta` emits `{Class: "kind", Word: w, Structural: true, DeployTraits: …}` for each, while `plugin-deploy-local`'s only capability is `deploy:local` — the DEPLOY target word, not the kind. The same correction unit 3 needed for `pod`; it is recorded on the tracker.

**The repo's own R10 harness is fixed in the same change.** The witness bed could not run from this repo's root at all after the deploy substrates were externalized (the project composed no `vm` substrate) — proven pre-existing by a control run on the pinned tree, root-caused in `plugin-fleet`'s refusal path, and fixed here because this change's gate cannot be green without it. Details, control output and the `.gitignore` correction are under **How tested**.

**The file-order move.** `schemaconcat.ConcatSchema` concatenates a schema dir's files in sorted order and strips only the package clause, and a CUE `import` must precede every declaration — so a module carries exactly ONE import and it must live in the file that sorts FIRST. `local.cue` sorts before `pod.cue`, so the module's single import moves out of `pod.cue` into `local.cue`. Both files' headers and this repo's `AGENTS.md` were updated in the same change: a stale "the import lives in `pod.cue`" is exactly the kind of sentence that makes the next unit break the load.

### The bed could not run at all — RCA, control, and the fix

The first bed run failed at `deploy-add`:

```console
charly: error: command "deploy": the "vm" deploy substrate is not available in this project —
  its deploy plugin (plugin-deploy-vm) is not in the candy closure. Compose it, or add_candy:
  something that pulls it in. A "vm" deploy compiles no primary image plan, so its ref was never
  a box or candy
```

**RCA (mechanism).** The deploy substrates are external per-project plugins now: a project that hosts a `vm:` deploy must compose `plugin-deploy-vm` into its candy closure, and this repo's manifest composed none. `plugin-fleet`'s `targetOnlyRoute`/`missingSubstrateErr` refuse before a VM is touched, which is the correct behaviour — the project, not the binary, owns the composition.

**Missed control.** The repo's `AGENTS.md` and the check skill both say the witness bed runs from its owning repo root; nothing in the repo proved it still could after the substrate externalization, and the repo's `.gitignore` still named a build-artifact directory (`output/`) that no producer has ever written.

**Blast radius.** Pre-existing and independent of this diff — proven by a CONTROL run of the SAME bed on the PINNED tree (the repo's unmodified `origin/main`), which fails at the same step:

```console
$ ./charly/bin/charly -C plugin-substrate check run check-substrate   # pinned tree, unmodified
charly check run check-substrate: [cleanup-members] PASS after 0s
charly check run check-substrate: FAIL (steps=7)
charly: error: command "check": deploy add check-substrate: deploy-add (charly deploy add) exited 1 after 3.911s
```

**Root fix, in this change** (the gate cannot be green without it): compose the substrate exactly as the org's own manifest records for opencharly/charly#1083 —

```yaml
import:
    - vmdeploy: '@github.com/opencharly/plugin-deploy-vm:v2026.314.0712'
```

— and correct the stale ignore (`.gitignore`: `output/` → `image/`, the directory `charly vm build` actually writes). A nested `local:` member needs no import: `plugin-fleet` routes `local` to the host's own shell. After the fix:
