## Summary

Re-pin the substrate structural-kind plugin (the 10th compiled-in plugin in the Cutover C wave) onto the settled contracts: the member-tree IR (spec #105/#107's uniform ordered Member tree, the position-derived DeployLevelMembers/InSubstrateMembers/MemberByName/HasMembers consult surface) and the substrate declared-fields channel (sdk #221/#225: a declared #Deploy body field is DATA — the parse never looks inside its value).

**THE SCHEMA FIX:** the pod/vm/kubernetes/local/android substrate kinds declare `InputDef: ""` — the pod body is validated HOST-side against the kept `#<Kind>Value` core def and the Fleet gate (`spec.ValidateDeploymentTree`), both supplied by the spec module this plugin embeds. Under the pre-wave pin (spec v0.2026241.1322, also the latest release tag v2026.242.0533), the canonical imageless agent_provisioned iterate-entity pod (`agent_provisioned: true` + an `iterate:` block, NO `image:`) failed the substrate load/validate chain — the `iterate:` block was misclassified as an in-substrate member (kind-word key `agent:` inside its value mapping) and the imageless shape failed the box-required validator — so the node VANISHED from the resolved fleet ("no entity check-agent-live") across the charly-cli + 3 iterate{agent:} beds, distro-arch check-agent-live, and ALL distro-fedora pod beds. The settled pins ARE the fix: spec v0.2026249.2215 carries the AgentProvisioned exemption in `ValidateDeployRequiresBox` (image optional when agent_provisioned is declared) and sdk v0.2026249.2239 carries the declared-fields guard (`TestParse_SubstrateDeclaredIterateStaysData`) that keeps `iterate:` DATA. No plugin-local CUE input-def change exists or is needed — `InputDef: ""` on all five words is unchanged.

**IDENTIFIERS MIGRATED (one compile break, tests only):** the android status-collector fixture's former `.Children` dual-map literal → the position-derived member tree (`Member: []spec.Member` with `Position: spec.PositionInSubstrate` — in-substrate members keep the dotted identity `FleetWalkPreOrder` walks). Production code needed no migration (it consults via `deploykit.FleetWalkPreOrder`, which is already member-tree-native).
